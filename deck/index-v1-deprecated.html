Chapter 01 — SDD

Spec-driven
development.

The spec is the source of truth. Code is a compiled artifact of it.

brainstorm → plan → tasks → implement → verify

SDD inverts the usual flow. We don't write code and then describe it — we describe it, get sign-off, then the agent compiles. Specs are versioned, reviewed, and become the contract for every agent that touches the codebase.
SDD in action

Same model.
Different output.

Vibes prompt

add a login page with google auth
and store the session somewhere

Result: 4 files, 0 tests, 3 assumptions, breaks in production on day 2.

Spec-driven prompt

# Auth spec
- Provider: Google OAuth (id_token only)
- Session: HTTP-only cookie, 7d expiry
- Storage: Convex `sessions` table
- Acceptance:
  - sign-in returns 302 to /app
  - invalid id_token returns 401
  - cookie unset on /logout

Result: 1 spec → 1 plan → 4 PRs, each green, each reviewable in 90 seconds.

The spec doesn't slow you down. The first 90 seconds of typing buys hours of agent autonomy. The acceptance bullets become the test names.
Chapter 02 — TDD

The agent
writes the
failing test first.

Red is the only proof your prompt was understood. Green is the only proof it's done.

TDD for agents inverts the usual "agent ships, you test." The agent must produce a failing test that encodes the acceptance criterion before writing a single line of implementation. If the test isn't red for the right reason, the prompt was wrong — not the code.
TDD receipt

Red → green → commit.

// step 1 — agent commits a failing test
test("rejects expired session cookie", async () => {
  const res = await app.request("/api/me", {
    headers: { cookie: `sid=${expiredSid}` },
  });
  expect(res.status).toBe(401);
});
// → FAIL: received 200

// step 2 — agent fixes implementation
- const session = await db.get("sessions", sid);
+ const session = await db.get("sessions", sid);
+ if (!session || session.expiresAt < Date.now()) return c.json({}, 401);

// step 3 — green. atomic commit.
$ git log -1 --oneline
3f9a1c2  fix(auth): reject expired session cookie

One acceptance line. One test. One commit. Reviewable in 30 seconds.

Show this commit was authored by the agent in a worktree. Each AC = one red test = one atomic commit. Reviewer sees the contract, the proof of failure, and the fix. No archaeology required.
Chapter 03 — Skills

Skills
are the new
function calls.

A skill is a name, a description, and a body. The agent reads the description and decides when to invoke. Lazy-loaded. Composable. Versioned.

The agent doesn't memorize every workflow. It memorizes the *catalog* — and pulls the body only when needed. This is how a single agent can hold 200+ workflows without burning context. Skills are to agents what packages are to npm.
Skill anatomy

Frontmatter + body.
That's the whole thing.

---
name: brainstorming
description: Use this before any creative work —
  creating features, building components, adding
  functionality. Explores intent and design before
  implementation.
---

# Brainstorming Ideas Into Designs

Help turn ideas into fully-formed designs through
natural collaborative dialogue.

1. Explore project context
2. Ask clarifying questions, one at a time
3. Propose 2-3 approaches with trade-offs
4. Present design, get approval per section
5. Write spec → invoke writing-plans
...

Source: superpowers:brainstorming. This deck was scoped through it.

Meta moment: this deck literally came out of the brainstorming skill. Show the description field is what the model matches on — not the body. Description is your search engine, body is your runbook.
Chapter 04 — Orchestration

One conductor.
Many specialists.

Parallel by default. Sequential only when one agent's output is another's input.

The conductor pattern. Main agent doesn't do the work — it dispatches. Specialists have narrow scope, narrow context, and return structured results. The bottleneck moves from "model is slow" to "you didn't fan out enough."
Orchestration DAG

Plan once.
Fan out four ways.

┌──────────────────────┐ │ conductor agent │ │ (plan + dispatch) │ └──────────┬───────────┘ │ spawn 4 in parallel ┌──────────────┬───┴────┬──────────────┐ ▼ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │codebase│ │ deps │ │history │ │ extern │ │ map │ │ scan │ │ read │ │ search │ └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘ └─────────────┴──┬───────┴────────────┘ ▼ ┌──────────────────┐ │ synthesizer │ │ → RESEARCH.md │ └──────────────────┘

Wall time of the slowest leaf, not the sum. 4 minutes instead of 16.

Pattern stolen from MapReduce. Hard part isn't the dispatch — it's the structured handoff. Each leaf returns a section, synthesizer composes the document. Same shape works for code review, audits, and migrations.
Real-world orchestration · 01

Phone in pocket.
Agents in the cloud.

vlad provisions a GCP VM and turns it into a mobile-first Claude Code rig. mosh keeps the connection alive across wifi swaps. tmux keeps every session pinned. Tailscale hides the VM behind a mesh — zero exposed ports.

Real-world orchestration · 02

One cockpit.
Every session, in flight.

Live state

Dashboard cards per session. JSONL watcher tails ~/.claude/projects/*. Transcript, tmux mirror, git diff, files — all real-time over WebSocket.

Take control

Tap a card → terminal view → toggle "Take control" → send-keys into tmux. Read-only by default, deep-link tokens expire in 15 min.

Auto-spawn

Cron schedules + GitHub webhook rules. issues:labeled bug → spawn a session with templated prompt → ntfy fires when ready.

┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ GitHub │ │ cron │ │ manual │ │ webhook │ │ scheduler │ │ CLI │ └──────┬──────┘ └──────┬──────┘ └──────┬──────┘ └──────────────────┼──────────────────┘ ▼ ┌───────────────────┐ │ vlad-cockpit │ ← daemon (bun) │ spawn · watch · │ │ expose · notify │ └─────────┬─────────┘ ┌─────────────┼─────────────┐ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ │claude 1│ │claude 2│ │claude N│ │worktree│ │worktree│ │worktree│ └────────┘ └────────┘ └────────┘ │ ▼ Tailscale Funnel · 3000 phone · laptop · tablet

SQLite state, HMAC-signed deep links, GitHub OAuth + allow-list. Single user, many agents, one URL.

This is the layer above vlad. If vlad is the runway, vlad-cockpit is air traffic control. The daemon watches every Claude session JSONL, mirrors tmux over WebSocket, and exposes a Next.js cockpit at one Tailscale Funnel URL. Cron and webhooks turn it from "operator console" into "autonomous swarm" — issues get labeled, a session spawns, runs the agent, pushes a notification, I open the deep link and review or take over. Chapter 05 — E2E

The browser
is the
final gate.

Type-checks lie. Unit tests lie. The DOM doesn't.

Until the agent has clicked the button and asserted the result, the feature isn't done. Playwright, Puppeteer, Chrome-via-MCP — pick one. The agent itself drives the headless browser as part of the verification loop.
E2E in the loop

Agent ships.
Agent verifies.
Agent retries.

$ bun test:e2e tests/grant-submission.spec.ts

  ✓ submits proposal and routes to /pending          1.8s
  ✓ judge agent scores within 90s                    62.3s
  ✓ score persists to base-sepolia                    9.1s
  ✓ score reads back from on-chain                    3.4s

  4 passed (76.6s)

# agent reads the green output, marks task complete,
# opens PR. no human in the verify loop.

Headless Chrome + Foundry node + on-chain assertions. Same suite runs in CI and locally.

This is the ipe-city E2E suite, paraphrased. The on-chain assertion is the killer: not just "did the UI confirm" but "did the receipt land on Base Sepolia." That's the bar.
Chapter 06 — Frameworks

Pick your weapon.

FrameworkPhilosophyKiller moveReach for it when
Superpowers Brainstorm-first. TDD-disciplined. Skill catalog + design gates You want process before code.
GSD Milestone-driven. Phase-gated. Wave-based parallel execution You want shipped artifacts on a schedule.
OpenSpec Spec-as-contract. Diff-on-spec, not on code Multi-team work needs one source of truth.
GitHub Spec Kit Specification-first, GitHub-native. specify → plan → tasks → implement Your repo is your project management.

Different syntax. Same physics: spec → plan → atomic commit → verification.

Don't argue holy wars. Each one is a dialect of the same grammar. Pick the one that matches your team's existing habits. The skills underneath transfer.

Honest notes

What broke.
What stuck.

Broke

  • Vibes-first led to deleted tests by the agent itself.
  • Skill descriptions too vague → never invoked.
  • Parallel agents stomping shared files. Worktrees fixed it.
  • On-chain test cost > CI budget until we mocked the RPC layer.

Stuck

  • Atomic commits with the AC in the message.
  • Specs written in markdown next to code.
  • Verification skill runs before every "I'm done."
  • One conductor agent owns dispatch — never the model picking ad-hoc.
This is the honest slide. Tell the worktree story — first attempt was three agents in the same checkout, all editing package.json simultaneously. Worktrees solved it in an hour. Mention the verification-before-completion skill by name.
